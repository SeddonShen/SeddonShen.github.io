§ 0

导读:先说结论,再慢慢讲

假设你完全没读过这篇论文,我们从一个最日常的场景说起。

你平时用的 Claude Code、Codex CLI、Gemini CLI,听起来像是"一个 AI 在帮你写代码"。但拆开看,里面其实是两个东西:一个语言模型,加上包裹它的一整层运行时——决定给模型看什么、给它哪些工具、上下文装满了怎么办、哪些命令要先征求你同意、要不要派几个分身并行干活。论文把这层"壳"正式命名为 harness。

这个词的本义是马具:套在马身上的缰绳、马鞍、马镫那一套。马(模型)负责跑,harness 负责让你驾驭这匹马。这个比喻贯穿全文,也比"框架""脚手架"之类的翻译都更贴切——harness 不是让马跑得更快的引擎,而是让马的力气可用、可控、可协作的那套装备。

⏱ 三分钟版本(论文的全部核心)

  1. Agent = 模型 + harness。harness 有七个标准子系统:循环、模型集成、工具、上下文管理、安全、编排、扩展。11 个系统全都长这个骨架,无一例外。
  2. 两个刺眼的"没有"贯穿全部 400 万行代码:没有任何一个系统 import LangChain 这类通用 agent 框架;也没有任何一个用向量 embedding 做"RAG 检索代码库"。大家全部用手写循环 + ripgrep/glob 这类确定性检索。
  3. 收敛正在变成模仿:Codex 逐字抄走了 Claude Code 的 hook 命名体系,还做了"导入 Claude Code 会话"的功能。行业从各自探索变成了围绕一个事实标准收敛。
  4. 2026 上半年,harness 完成了从"工具"到"平台"的转身:变成可 import 的 SDK、有了插件市场和企业治理层,甚至出现了用一套 API 编排 11 个厂商 harness 的"元 harness"。
  5. 论文最后给了 18 条设计建议 + 一个约 90 行 Python 的最小可用 harness,一个框架依赖都没有,却直接落实了 18 条建议里的 10 条。这份笔记的第 7 节会把它一行行啃碎。

这份笔记怎么读:按顺序读就行,§1–§2 建立概念,§3 是全文最有意思的发现,§4 是七大子系统的细节之旅(八卦都收在折叠条里,想看再点开),§7 是重头戏——那 90 行代码。引用格式如 §9.5、观察 9 均指论文原文章节,方便你回原文对质。

关于可信度:这篇论文自己承认不 benchmark、不排名,只做解剖和比较("It does not benchmark or rank; it describes and compares how the systems are built")。另外它读的是 2026 年 4 月和 7 月两个时间点的源码快照——这个领域三个月就能变一副面孔,论文里有专门一章讲这 90 天里发生了什么。
§ 1

Harness 到底是什么:一句话定义和七件套

论文摘要第一句就把定义给全了,值得原样放这儿:

“An agent is a model plus a harness: the runtime that couples an LLM to the world through a loop, tools, context management, safety controls, orchestration, and extension surfaces.”—— 摘要。译:agent 就是模型加马具——一个通过循环、工具、上下文管理、安全控制、编排和扩展接口,把 LLM 耦合到真实世界上的运行时。

注意这句里冒号后面的六个词,加上"循环"所在的那个整体,就是论文反复使用的七大子系统骨架。为了防止概念混淆,论文还专门划了四个"不是"(§2.2),我按自己的理解转述一下:

  • 不是通用框架。LangChain、LlamaIndex 那类抽象层——事实上 11 个系统一个都没用(§3 细讲)。
  • 不是脚手架(scaffold)。脚手架是生成项目目录结构的模板;harness 是一直运行着、每秒钟都在做决策的运行时。
  • 不是测评外壳(eval harness)。评测领域也用 harness 这个词,指包裹模型跑 benchmark 的脚本,和这里的"生产运行时"是两回事。
  • 不是编排器(orchestrator)。多 agent 编排只是七个子系统之一,把整个 harness 等同于编排是把局部当整体。

我个人觉得最有用的心智模型是:harness 是驾驶舱,不是发动机。发动机(模型)决定马力上限,驾驶舱决定这匹马力能不能安全地变成位移。论文后面所有内容,都是在描述这 11 家公司分别怎么造驾驶舱。

§ 3

全文最反直觉的发现:两个"没有"

如果这篇论文只能记住一件事,我会选这个。两个在 LLM 应用圈被当作"标配"甚至"先进"的东西,在 400 万行生产代码里出现次数为——零。

0/11
没有框架
没有一个 agent 运行时 import LangChain、LangGraph、AutoGen、CrewAI、LlamaIndex、Genkit、ADK……全部是手写的异步循环。
0/11
没有向量 RAG
没有一个系统用 embedding 做"检索代码库"。全部用确定性检索:ripgrep、glob、tree-sitter、自动发现的 Markdown 上下文文件。
“Two absences survive a threefold corpus expansion: across roughly four million lines of Python, TypeScript, and Rust, no agent runtime imports a general-purpose agentic framework (…Gemini CLI uses neither of Google's own), and none retrieves code with vector embeddings.”—— 摘要。注意括号里那句:连 Gemini CLI 都不用 Google 自家的 Genkit 和 ADK。

为什么不用框架?

论文(观察 9 + 建议 15)给的理由,概括起来是"抽象税"框架的抽象层会把提示词和响应包起来,反而让你更难调试——这句话论文直接引自 Anthropic 工程师的忠告。而这些系统需要的循环本质上是"SDK 调用 + 一点胶水",手写 500 行以内就够,引入一个框架换不来什么。

最有意思的注脚是 LangChain 的反应。论文脚注记录:LangChain 对"没人用我"的回应不是辩解,而是自己做了一个 harness——基于 LangGraph 的 Deep Agents。而这个产品"独立收敛到了本语料记录的同一批约定上":SKILL.md 技能、渐进式披露……换句话说:框架厂商最终承认,harness 才是用户真正要买的东西。

为什么不用向量检索代码?

论文建议 8 的原文相当不客气:"不要在代码上建 RAG"。三个理由,每一个都挺硬:

  1. 代码有丰富的确定性结构——路径、语言服务器、tree-sitter 语法树。这些信号是语义相似度给不了的。
  2. 代码分钟级地在变,embedding 索引天然滞后,而 grep 永远是"此刻"的真相。
  3. grep 的结果是可复现、可解释的——agent 说"我是搜到这行才改的",你能验证;embedding 召回则像玄学。

一个常被忽略的细节:语料里确实出现了 embedding,但全部用在对话记忆上(OpenClaw 的混合搜索、Hermes 的可选插件),不是代码。而且 Hermes 用 SQLite 全文检索(FTS5)就在 64 万行代码的规模上把记忆搜索扛住了——连"记忆检索"都不一定需要向量。

🤔 思考题:如果你要给 agent 加"找到处理支付的那个文件"的能力,论文的答案是什么?
给它 grep/rg 工具加目录树浏览,让它自己搜"payment"、"charge"、"stripe" 这些关键词,顺藤摸瓜。模型的语义理解能力 + 确定性工具的组合,击败了预先建好的向量索引——这也正是这 11 个系统的共同选择。

📓 折叠:agent 停不下来怎么办?(死循环检测的众生相)

论文建议 18 的结论有点反直觉:Claude Code 和 Codex 至今没有自动死循环检测,照样是生产级产品。但"便宜的限制"已经成为标配底座:

• Mini-SWE-Agent(50 行循环!)都有 step 上限、成本上限,v2.4 还加了墙钟时间上限和"连续畸形响应"计数。
• OpenCode 的 doom-loop 检查就是一个"连续三次一模一样的调用"计数器,触发了就弹权限询问。
• Hermes 给调用签名做哈希,但硬停止默认是关的,只报警——它信任警告。
• 真正的重型投资:OpenHands 的五场景 StuckDetector、Gemini 的哈希+LLM 混合判断服务。

一句话:别过度工程化卡死检测,但那十几行的保险丝必须装。(90 行代码里的 _check_limits 就是这类保险丝,§7 见。)

4.2 模型集成:提示词里全是戏LLM Integration · 论文 §7

这一章的信息密度极高。两个结构性事实先立住:

  • 提示词跟模型版本走。Codex 每一代模型配一套提示词,而且现在直接从服务端的模型目录下发——提示词成了模型配置的一部分,不随 CLI 版本走。
  • 缓存经济学是真金白银。Claude Code 把提示词钉在一个 Blake2b 哈希的缓存边界上,静态前缀跨会话全局缓存;派 fork 子 agent 时字节级继承父提示词,就是为了共享这份缓存。Codex 用 thread_id 派生缓存键。Pi 干脆为每家模型维护一套"缓存方言"开关(论文叫 cache-dialect fanout)。

论文观察 3 给这一章下了个很好的判语,大意是:提示词的措辞在工程经验汇聚的地方收敛,然后变薄——行为规则正在从提示词散文搬家到配置文件和代码里(hook、策略引擎)。这个"搬家"动作是 §5 平台化叙事的前奏。

📓 折叠:提示词八卦合集(论文 §7.3,瓜田浓度预警)

• 自我介绍卷起来了。OpenCode 的开场白:"You are OpenCode, the best coding agent on the planet."(你是 OpenCode,星球上最强的编码 agent。)

• 禁 emoji 军备竞赛。Mistral Vibe 拿了最严禁令:"任何 emoji 都不许用。不许笑脸、图标、旗帜或 Unicode 符号……适用于正文、代码注释和 commit 信息。"OpenCode 的 GPT 模式禁 emoji、禁 em dash(——),连"Done —"“Got it,”这类开场白都禁。Claude Code 温和些:用户明确要求才能用。

4.3 工具系统:一个 bash 走天下,109 个也都有理Tools · 论文 §8

工具数量的光谱两端都站着理直气壮的系统:Mini-SWE-Agent 只给一个 bash(“一切皆命令行”,74%+ 的成绩证明这条路能走);OpenClaw 109+ 个工具(毕竟要处理媒体和多渠道消息)。Pi 把"少"做成了哲学:7 个内置工具,默认只暴露 4 个,其余通过扩展按需加载。

共识核心就是五件套:bash、read_file、write_file、search_replace、grep/glob。工具多到一定程度(论文给的阈值是 ~15 个)就必须做延迟加载:Claude Code 用 ToolSearch 工具让模型"搜索要用的工具",初始提示词缩水约 40%;Codex 独立收敛到了同款方案(BM25 排序的 tool_search);Hermes 更激进——MCP 工具目录一旦要吃掉上下文窗口的 10%,就折叠成三个"桥接工具"。

论文观察 4 说,文件编辑策略是决定"改代码"能力最重要的因素之一。这个领域的战争史大致是:整文件重写 → diff/patch → 收敛到"唯一子串替换"。现在的两大阵营:

  • 精确派(前沿模型):Claude Code 要求精确匹配;Mistral Vibe 2026 年中直接删掉了自己的 SEARCH/REPLACE 工具改走精确匹配;Pi 只做 Unicode/空白规范化外加字节级保真覆盖层。
  • 容错派(更广的模型谱系):OpenCode 九级回退串(Levenshtein 相似度 0.65 起步);Hermes 九策略链;Aider 的 RelativeIndenter 专治缩进漂移。

还有个第三条路挺妙:Gemini CLI 匹配失败时,调用一次小 LLM 去修格式——用模型修模型。而所有系统都躲着一条路:按行号编辑。模型数行号比做上下文匹配更容易漂,这是血泪共识。

4.4 记忆与上下文:压缩已谢幕,记忆是新前线Memory · 论文 §9

agent 的全部状态就是上下文窗口里的对话,而窗口会满。这个问题的第一阶段解法——阈值压缩——已经收敛到"解决了"的程度,7 个系统殊途同归:

  • Claude Code:token 估算进入窗口下方 13,000 的缓冲区就触发(AUTOCOMPACT_BUFFER_TOKENS = 13000,环境变量可覆盖);
  • Gemini CLI:窗口用到 50% 时压缩,保留最近 30% 原文;
  • Pi / OpenCode:上一次的摘要会传回给模型做增量合并,避免从头重总结把早期决策弄丢;
  • Mistral Vibe:压缩后把用户的历史消息重新注入信封,而且同一套例程在中途撞上 ContextTooLong 报错时应急复用。

论文观察 5 判定:2026 年的前沿已经从压缩转移到持久记忆。新名词一个比一个有意思:Codex 的"agent 自维护记忆管线"(让沙箱里的子 agent 管理长期记忆文件)、Hermes 的 lineage compaction(压缩 = 结束当前会话、开新会话,全部历史进 lineage 库,永不销毁)、Claude Code 私有的 MEMORY.md 项目索引、OpenClaw 按 agent/会话落盘的 JSONL 转录。而记忆检索的天花板,SQLite 全文检索就够(Hermes,64 万行规模)——确定性检索的胜利从代码延伸到了记忆。

还有个特别实用的部分:项目上下文文件的自动发现,就是那批 AGENTS.md/CLAUDE.md/GEMINI.md。每家的走法都不一样,而且都有明确的取舍:

系统上下文发现策略

4.5 安全与权限:从"先问后做"到"操作系统级硬隔离"Safety · 论文 §10

论文给安全章节画了一条时间线:2024 年的主流思路是可逆性(问你一句再动手);2025 年风向变成 OS 加固(bash 用户限制、Landlock、各类沙箱)。理由不复杂:agent 获得的自主性越大,权限对话框就越跟不上——而模型永远可以被提示词注入攻破,只有操作系统不会。

两个标杆设计值得细看:

  • Claude Code 三层权限:静态规则(最快、最少上下文)→ LLM 辅助判断 → 交互式对话框(最慢、最可靠)。后台 agent 和 fork 子 agent 只有前两层可用——它们的"对话框"会直接解析为拒绝,防止无人值守的 agent 卡在等确认上。
  • Codex 四层堆栈:Starlark 策略引擎 → 生命周期 hooks → 审批门 → 原生跨平台沙箱(Linux 把 Bubblewrap 直接内置进了代码库,macOS 用 Seatbelt)。Starlark 这个选择很讲究——策略文件是可执行代码,还带解析时校验的内联测试用例:
prefix_rule(
    pattern = ["git", "status"],
    decision = "allow",
    match    = [["git", "status"], ["git", "status", "--short"]],
    not_match = [["git", "push"]],      # 策略自带反例,加载时就验证
)

OpenCode 的思路则完全相反:语法感知的命令权限——每条 bash 命令用 tree-sitter 解析(bash 和 PowerShell 语法),"always allow" 的授权按命令元数精确到 git commit * 而不是一刀切放行 git;项目目录内默认全放行,只有越出项目、读 .env、死循环才拦。默认宽 Codex 一整头。

Pi 的姿态最坦率:论文引用它(大意)"把权限系统误解为安全边界是要出事的",宣布上下文文件的提示词注入防不住,干脆明说接受这个攻击面,把信任门控只用在仓库控制的配置加载上,审计靠只追加的会话树。

🤔 思考题:为什么"无人值守的后台 agent"反而不能给它弹窗确认的能力?
因为它没人可问。Claude Code 的做法是:后台/分叉子 agent 的交互层直接解析为"拒绝"——宁可任务失败重来,也不能让整个流水线挂在一个永远没人点的对话框上。交互权限只属于前台、有人看着的那个 agent。

4.6 多 agent 编排:六种模式,一条警告Orchestration · 论文 §11

论文 §11.1 的六种编排模式,从简到繁:

  1. 单 agent(Mini-SWE-Agent、Aider、Pi 核心)——没有分身就是最好的分身;
  2. 顺序委托(Mistral Vibe):父 agent 用 task 工具派一个子 agent,原地等结果;
  3. 并行子会话(OpenHands、OpenCode):子任务是独立会话,一条消息里的多个调用并发跑;
  4. 层级线程树 + 扇出(Codex):专用线程、fork 继承控制、map-reduce 式扇出、父子拓扑持久化;
  5. 递归组合(Claude Code):agent 生 agent 可无限嵌套,fork 时字节级继承提示词共享缓存;
  6. 注册表 + 跨进程协议(Gemini CLI 的 A2A、OpenClaw 的 ACP、Hermes 的 SQLite 黑板看板群)。

警告来自建议 12:在能指着具体场景说出"并行上下文隔离确实赢过串行"之前,保持单 agent。多 agent 系统的 token 消耗大约是单聊基线的 15 倍,而"大多数编码任务里真正可并行的部分比研究任务少得多"。Mistral Vibe 那个顺序委托的 task 工具,论文评价是"对大多数编码工作流已经够用"。

跨进程协议这块还有个新剧情:ACP(2026.2 由 Zed 推出)在 6/11 的系统里落地,并且长出了论文所说的第三种角色——harness 托管:OpenHands 现在能把 Claude Code、Codex、Gemini CLI 当成可互换的 ACP 后端跑。IDE 之外,harness 之间也开始互相"寄生"了。

4.7 扩展机制:Skills 反超 MCP 的那一季Extensibility · 论文 §12

4 月的快照里,SKILL.md 技能和 MCP 还打平;7 月的语料打破了平衡——技能 9/11,MCP 8/11。决定性一票是 Pi:它实现了 agentskills.io 技能标准,同时彻底拒绝 MCP。"技能即 MCP 替代品"从一个怪念头变成了明确立场。

两者在论文里的分工建议(建议 14)很清晰:技能装"能力模板"(工作流、领域知识、操作配方——本质是结构化的提示词包),MCP 装"外部集成"(Slack、数据库、内部 API——本质是进程和协议)。按这个优先级,先技能后 MCP。

技能生态已经卷出了新高度:跨厂商发现(OpenCode 直接读 ~/.claude/skills 目录——用户给 Claude 装的技能,OpenCode 白嫖)、注册表、信任分级、隔离扫描,以及语料里第一次出现的 agent 自己写的技能(Hermes 的自我改进循环:经验沉淀成技能文件,技能带版本演化)。论文提醒:装第三方技能要像装包一样对待——信任分级、扫描、隔离(Hermes 是基线)。

至于 hooks——这个概念的原创是 Claude Code,而现在 Codex 的 hooks 事件命名表(PreToolUse、PostToolUse、PreCompact、SubagentStart……)已经和 Claude Code 近乎逐字相同,只多了一个 Claude Code 没有的 PostCompact。这是 §5 那个"收敛变模仿"故事最硬的一块化石。

§ 5

90 天纵向对比:收敛变成模仿,harness 变成平台

论文把 4 月解剖过的 8 个系统在 7 月重新钉住同一批 commit 再读一遍,得到一份罕见的"受控演化样本"。结论浓缩成两句话,都值得原味品尝:

“The diff shows convergence becoming imitation (Codex adopts Claude Code's hook vocabulary verbatim and ships an importer for its sessions and settings; OpenHands reads Claude Code's plugin format), while behavioral policy migrates from prompt prose to configuration.”—— 摘要。译:差异对比显示,收敛正在变成模仿(Codex 逐字采用 Claude Code 的 hook 词汇表,还发布了它的会话与设置的导入器;OpenHands 读 Claude Code 的插件格式),与此同时,行为策略正从提示词散文迁移到配置。

先看速度。Codex 的代码量单季度从 62.1 万行涨到约 112 万行 Rust(crate 数 89→126),相当于每几周长出一个中型开源项目;Mistral Vibe 涨了 77%(3.56 万→6.3 万行);OpenHands 直接重新架构成了 SDK。论文为此专门立了个方法论规矩:清点式结论(inventory)必须标注日期,结构性结论(structure)才敢谈持久——而且这三个月里,4 月版的 13 条观察中有 3 条被实质性修订。诚实得让人有好感。

"收敛变模仿"最直观的三块证据:Codex 的 hooks 词汇表逐字抄 Claude Code;Codex 做了 Claude Code 的会话与设置导入器(降低你的切换成本——注意,是往自家导入,不是导出);OpenHands 读 Claude Code 的插件格式。论文的评语很冷:这不是巧合,是围绕一个事实标准的系统性收敛。

平台转向:论文的总论点

论文的最终论点(观察 12):2026 上半年,coding harness 完成了从"工具"到"平台"的转身。四条证据链,每条都能在源码里指认:

  1. harness 变成可 import 的 SDK(Claude Agent SDK、openai-codex、openhands-sdk)——论文建议 15 的 2026 注脚:"框架层"现在就是这些 harness SDK,模式已经内置;而框架厂商反过来做了 harness(LangChain 的 Deep Agents)。
  2. 市场与切换成本工具出现:插件市场、会话导入器、格式互通。
  3. 企业治理层出现:策略引擎、审计轨迹、遥测——安全从"产品功能"升级为"平台属性"。
  4. agent 被当成模型暴露:OpenAI 兼容端点后面坐着的不再是模型,而是一整个 agent;Omnigent 这种元 harness 用一套 API 编排 11 个厂商 harness,论文的原话是"重新实现昂贵的部分,套利专有的部分"。

结合 Aider 的停更和被收购语境,论文给这个行当下了个定语:harness 这一层"是厂商会收购、贴牌、上锁的战略性基础设施"。个人体会:这一章读完,你对"哪家 CLI 好用"的判断会降维成次要问题——真正的竞争已经上移到"谁成为别人都要兼容的那个标准"。目前看,那个标准长得很像 Claude Code。

第 7–8 行是全篇最值钱的两行。Protocol 是"结构化鸭子类型":任何拥有 complete 方法的对象,都是模型。这 90 行代码对 GPT、Claude、本地 Qwen 一无所知,它只认识这个签名。换供应商 = 写一个几十行的适配器类(见 G 卡),agent 代码零改动——这就是 R2"provider-first + generic fallback"的骨架形态,也是 11/11 系统共有的第一道抽象。
